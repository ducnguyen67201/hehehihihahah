# Positioning: Resolution OS

## Locked positioning

- `Resolution OS for enterprise technical issues`
- `AI copilot for post-sales technical operations`
- `Closed-loop issue resolution for B2B support + engineering`

## Category

- This product is not a support inbox.
- This product is not a generic helpdesk.
- This product is not a chatbot for customer support.
- This product is a resolution layer that helps teams move from customer-reported issue to next action to final closure.

## Core promise

- Turn messy technical support issues into structured, actionable resolution flows.
- Help support decide the next best action.
- Help engineering receive cleaner escalation context.
- Help teams close the loop with the customer after the issue is fixed.

## Primary user

- Primary user:
  - Support engineer, solutions engineer, founder, or operator handling customer-facing conversations that may turn into issues, requests, or follow-up work
- Secondary users:
  - Engineering owners receiving escalations
  - Product owners reviewing requests and patterns
  - Technical account or post-sales operations teams following issue status

## Primary user pain

- A customer conversation can contain many different signals:
  - technical issue
  - bug report
  - feature request
  - product confusion
  - follow-up question
- These signals often arrive in chat, inboxes, or ad hoc conversations, not in a clean structured format.
- The operator has to decide what kind of thing this is, whether it needs investigation, whether it belongs to product or engineering, and what should happen next.
- That work requires repeated context switching across conversations, notes, RCA tools, product context, and internal coordination.
- The same conversation gets rewritten multiple times into different forms:
  - internal understanding
  - escalation or handoff
  - reply back to the customer
- This wastes time, creates ambiguity, and increases the chance that important follow-up work falls through the cracks.

## Core job to be done

- When a customer-facing conversation happens, the operator needs to quickly understand what kind of case it is, what context is missing, and what the next best action should be, without manually stitching information across multiple tools.

## Current broken workflow

1. Customer sends a message, question, complaint, or request.
2. The operator reads the conversation and tries to figure out what category it belongs to.
3. The operator jumps into other tools to gather product and account context.
4. The operator decides whether it is:
   - a bug or technical issue
   - a feature request
   - a question that can be answered directly
   - something that needs escalation
5. The operator rewrites the conversation into an internal artifact.
6. The internal team handles the request or issue.
7. Someone has to remember to update the customer later.

## Desired workflow

1. Customer sends a message, request, or report.
2. The conversation is turned into a structured internal case automatically.
3. The system identifies the case type and summarizes it.
4. The system highlights missing context and recommends the next best action.
5. The system drafts the right internal or external response.
6. The case stays linked to downstream action, ownership, and resolution.
7. When there is an outcome, the system drafts the follow-up back to the customer.

## Why this user first

- This user feels the pain most directly.
- This user sits between the customer conversation and the internal team that needs to act.
- This user pays the cost of context switching every time the conversation is unclear or unstructured.
- This user is the fastest path to a credible enterprise demo because the workflow is visible, common, and easy to understand.

## Core workflow

1. Customer reports a technical issue.
2. The system structures and classifies the issue.
3. The system recommends the next best action.
4. The system drafts the right follow-up or escalation.
5. The system tracks the issue through resolution.
6. The system helps close the loop with the customer.

## Positioning guardrails

- Optimize for technical issue resolution, not generic support volume.
- Focus on support + engineering coordination, not broad CRM workflows.
- Keep humans in the loop for customer-facing actions.
- Win on depth of issue understanding, not breadth of communication channels.
- Build around resolution quality, reproducibility, and closure.

- `Closed-loop resolution for support and engineering`
